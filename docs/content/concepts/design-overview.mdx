This page explains why Collegium exists, what it commits to, and how the pieces fit together. Read it to decide whether the design matches your problem. Each page after it takes one part deeper.

## The prevailing shape

Most agent frameworks share one shape: a capable model, a shell, and a loop that iterates unattended until the task looks done. Almost everything about that shape was chosen for writing software. A failed attempt costs nothing, because the work happens in a sandbox or a branch. You review output as a diff before it ships. Retrying is free, so aggressive retries are a feature. Supervision can be an afterthought, because the blast radius of a bad run is a rejected pull request.

Point that shape at business work and every one of those assumptions inverts. An email to a client is visible the moment it sends, and nobody can unsend it. Nobody reviews a sent message as a diff. The retry that makes a coding agent resilient becomes a liability. When a send times out ambiguously, a coding agent's instinct is to try again, and trying again is how a client gets the same email twice. Frameworks of this shape also tend to treat instructions as advisory. They spawn ephemeral workers whose output outlives them. They keep coordination state in process memory where nobody can see it. None of that is malicious. It is a set of defaults built for one kind of work, applied to another.

Collegium is a structural response: a framework where supervision is the design center rather than a feature, built for the work that isn't writing software.

## The five commitments

**Chat is the only substrate.** Agents are bot accounts in your team's Mattermost workspace, and every activation is a post. There is no internal message bus, no scheduler calling agents behind the scenes, and no work that exists only in process memory. If work is happening, there is a post anyone in the channel can scroll to. Debugging is scrollback. The cost is that everything routes through one system. That cost is accepted, because a coordination layer nobody can see is how work goes wrong invisibly.

**No ambient code execution.** Every capability is a hand-written TypeScript function with a schema, fixed at boot. There is no dynamic tool creation and no runtime agent spawning. Shell access exists, but as an explicit per-agent grant with every command individually approved. Shell commands run under a dedicated OS user that owns its home directory and nothing else. You can enumerate an agent's entire reach by reading its configuration. The cost is flexibility. An agent can't invent a capability mid-task, and that is the point.

**Deterministic activation.** Code decides when an agent acts. The model decides what to do once activated. An agent can't schedule itself, wake itself, or extend its own operating window. Scheduled and external work arrives as triggers: deterministic intake that records the event and announces it in the channel, where it starts an ordinary turn. The cost is that idle agents do nothing. An agent with initiative and idle cycles finds work nobody asked for.

**Clean stop over graceful degradation.** When anything goes wrong, the turn ends with a visible notice. That covers a denial, a malformed response, an exhausted budget, and an ambiguous outcome alike. Nothing retries around a failure, degrades quietly, or improvises an alternative path. Transport blips are retried invisibly because they are not failures of intent. Everything else stops. The cost is interruptions, and the trade is deliberate. A system that degrades gracefully hides its failures. An agent that has been quietly wrong for six hours is worse than one that stopped and said so.

**Visibility is not consent.** The framework records and surfaces everything an agent does, but only consequential actions block for approval. Reads run freely. Sends, writes, and commands stop and show their entire payload. The distinction is deliberate. Approval frequency is inversely related to approval quality, and a gate that fires on everything gets answered reflexively until it stops being a control. Ungated never means unsupervised: every call is traced, and you can retrieve the record on demand.

## How the pieces fit

You declare agents in one configuration file: name, persona, model, tools, skills. Before the app boots, provisioning reconciles Mattermost against that declaration, creating bot accounts and tokens. At runtime, a post that addresses an agent starts a turn. The turn is the unit of execution: the agent assembles context, calls its model, runs tools, and produces output. While a turn runs, its channel shows a status post that updates in place, one line per tool call. When the agent reaches a consequential action, an approval prompt blocks the turn with the full payload. Any human in the channel can decide it. Work addressed to a busy agent queues visibly and drains into a single turn when the channel goes idle. External events, such as mail arriving or a webhook firing, become triggers that the system bot announces in the channel, starting ordinary turns. When anything fails, the turn stops with a notice. A restart abandons in-flight work rather than resuming it. Framework-wide limits bound delegation depth and total activity, enforced in code rather than in prompts.

Key business logic doesn't live in prompts at all. Plugins you write contribute tools and durable records as deterministic TypeScript, reviewed once and granted per agent. What must happen in order is code. What benefits from judgment is the agent's.
