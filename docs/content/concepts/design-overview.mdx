Why Collegium exists, what it commits to, and how the pieces fit together. This is the page for deciding whether the design matches the problem; the pages after it each take one part deeper.

## The prevailing shape

Most agent frameworks share one shape: a capable model, a shell, and a loop that iterates unattended until the task looks done. Almost everything about that shape was chosen for writing software. A failed attempt costs nothing, because the work happens in a sandbox or a branch. Output is reviewed as a diff before it ships. Retrying is free, so aggressive retries are a feature. Supervision can be an afterthought, because the blast radius of a bad run is a rejected pull request.

Point that shape at business work and every one of those assumptions inverts. An email to a client is visible the moment it sends and cannot be unsent. Nobody reviews a sent message as a diff. And the retry that makes a coding agent resilient becomes a liability: when a send times out ambiguously, a coding agent's instinct is to try again, and trying again is how a client gets the same email twice. Frameworks of this shape also tend to treat instructions as advisory, to spawn ephemeral workers whose output outlives them, and to keep their coordination state in process memory where nobody can see it. None of that is malicious. It is a set of defaults built for one kind of work, applied to another.

Collegium is a structural response: a framework where supervision is the design center rather than a feature, built for the work that is not writing software.

## The five commitments

**Chat is the only substrate.** Agents are bot accounts in the team's Mattermost workspace, and every activation is a post. There is no internal message bus, no scheduler calling agents behind the scenes, and no work that exists only in process memory. If work is happening, there is a post anyone in the channel can scroll to; debugging is scrollback. The cost is that everything routes through one system, and we accept that: a coordination layer nobody can see is how work goes wrong invisibly.

**No ambient code execution.** Every capability is a hand-written TypeScript function with a schema, fixed at boot. There is no dynamic tool creation and no runtime agent spawning. Shell access exists, but as an explicit per-agent grant with every command individually approved, running under a dedicated OS user that owns its home directory and nothing else. An agent's entire reach is enumerable by reading its configuration. The cost is flexibility: an agent cannot invent a capability mid-task, and that is the point.

**Deterministic activation.** Code decides when an agent acts; the model decides what to do once activated. An agent cannot schedule itself, wake itself, or extend its own operating window. Scheduled and external work arrives as triggers: deterministic intake that records the event and announces it in the channel, where it starts an ordinary turn. The cost is that idle agents do nothing. An agent with initiative and idle cycles finds work nobody asked for.

**Clean stop over graceful degradation.** When anything goes wrong (a denial, a malformed response, an exhausted budget, an ambiguous outcome) the turn ends with a visible notice. Nothing retries around a failure, degrades quietly, or improvises an alternative path. Transport blips are retried invisibly because they are not failures of intent; everything else stops. The cost is interruptions, and we take that trade deliberately: a system that degrades gracefully hides its failures, and an agent that has been quietly wrong for six hours is worse than one that stopped and said so.

**Visibility is not consent.** Everything an agent does is recorded and surfaced, but only consequential actions block for approval. Reads run freely; sends, writes, and commands stop and show their entire payload. The distinction is deliberate: approval frequency is inversely related to approval quality, and a gate that fires on everything is answered reflexively until it stops being a control. Ungated never means unsupervised: every call is traced, and the record is retrievable on demand.

## How the pieces fit

An operator declares agents in one configuration file: name, persona, model, tools, skills. Before the app boots, provisioning reconciles Mattermost against that declaration, creating bot accounts and tokens. At runtime, a post that addresses an agent starts a turn: the unit of execution in which the agent assembles context, calls its model, runs tools, and produces output. While a turn runs, its channel shows a status post that updates in place, one line per tool call. When the agent reaches a consequential action, an approval prompt blocks the turn with the full payload; any human in the channel can decide it. Work addressed to a busy agent queues visibly and drains into a single turn when the channel goes idle. External events (mail arriving, a webhook firing) become triggers that the system bot announces in the channel, starting ordinary turns. When anything fails, the turn stops with a notice; a restart abandons in-flight work rather than resuming it; and framework-wide limits bound delegation depth and total activity, enforced in code rather than in prompts.

Key business logic does not live in prompts at all. Operator-written plugins contribute tools and durable records as deterministic TypeScript, reviewed once and granted per agent. What must happen in order is code; what benefits from judgment is the agent's.
