This page describes the assumptions behind Collegium's design, the constraints that follow from them, and how the parts fit together. The pages after it each cover one part in more depth.

## Assumptions About the Work

Collegium is built for non-engineering work: email, research, and follow-up tasks. This kind of work differs from writing software in ways that shape the design.

An action is visible to other people as soon as it happens. An email reaches its recipient when it sends. There is no stage where someone reviews the output before it takes effect.

Many actions can't be undone. A sent message can't be recalled. An instruction to a colleague can't be unsaid.

Retrying is not safe. If a send times out without a clear result, retrying it can deliver the same message twice.

A framework that lets a model iterate unattended, retry on failure, and improvise around errors produces mistakes that people see and can't reverse. Collegium constrains agents so that people see each step and decide the consequential ones.

## Design Constraints

**Chat is the only substrate.** Agents are bot accounts in your team's Mattermost workspace, and every activation is a post. There is no internal message bus, no scheduler that calls agents directly, and no work that exists only in process memory. If work is happening, a post in the channel started it. The cost is that everything routes through one system. The benefit is that no coordination happens where nobody can see it.

**No ambient code execution.** Every capability is a hand-written TypeScript function with a schema, fixed at boot. There is no dynamic tool creation and no runtime agent spawning. Shell access exists as an explicit per-agent grant with every command individually approved. Shell commands run under a dedicated OS user that owns its home directory and nothing else. You can enumerate an agent's entire reach by reading its configuration. The cost is that an agent can't gain a capability during a task.

**Deterministic activation.** Code decides when an agent acts. The model decides what to do once activated. An agent can't schedule itself, wake itself, or extend its own operating window. Scheduled and external work arrives as triggers: code records the event and announces it in the channel, where it starts an ordinary turn. The cost is that idle agents do nothing.

**Clean stop over graceful degradation.** When anything goes wrong, the turn ends with a visible notice. That covers a denial, a malformed response, an exhausted budget, and an ambiguous outcome alike. Nothing retries around a failure, degrades quietly, or improvises an alternative path. Transport errors are retried invisibly because they are not failures of intent. Everything else stops. The cost is interruptions. The benefit is that a failure is visible when it happens rather than hours later.

**Visibility is not consent.** The framework records and surfaces everything an agent does, but only consequential actions block for approval. Reads run without approval. Sends, writes, and commands stop and show their entire payload. The reasoning is that approval quality falls as approval frequency rises. A gate that fires on everything gets answered without reading. Ungated does not mean unsupervised: every call is traced, and you can retrieve the record on demand.

## How the Parts Fit

You declare agents in one configuration file: name, persona, model, tools, skills. Before the app boots, provisioning reconciles Mattermost against that declaration, creating bot accounts and tokens. At runtime, a post that addresses an agent starts a turn. The turn is the unit of execution: the agent assembles context, calls its model, runs tools, and produces output. While a turn runs, its channel shows a status post that updates in place, one line per tool call. When the agent reaches a consequential action, an approval prompt blocks the turn with the full payload. Any human in the channel can decide it. Work addressed to a busy agent queues visibly and drains into a single turn when the channel goes idle. External events, such as mail arriving or a webhook firing, become triggers that the system bot announces in the channel, starting ordinary turns. When anything fails, the turn stops with a notice. A restart abandons in-flight work rather than resuming it. Framework-wide limits bound delegation depth and total activity, enforced in code rather than in prompts.

Business logic that must run in a fixed order belongs in plugins rather than prompts. A plugin contributes tools and durable records as TypeScript, reviewed once and granted per agent.
