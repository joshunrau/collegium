## Tools

Every capability an agent has is a hand-written TypeScript function exposed to the model with a schema, one tool per action. There is no dynamic tool creation. The tool set is fixed when the process boots, and each agent holds only what its configuration grants.

Tools come in toolsets. A toolset is a namespace and everything that belongs to it: its tools, the services they reach, the settings that configure them, and the skills they ship. A tool's name is its namespace plus its action: `mail::send`, `memory::read`, `web::navigate`. A grant is a namespace or a single tool. `"mail"` grants every mail tool; `"mail::list"` grants one. Each toolset's settings live under the same namespace in configuration, validated against the schema the toolset itself declares. Granting mail without a mailbox is refused at boot because the mail settings schema says so, not because anyone maintains that rule.

Every tool declares two things about itself. Whether it gates is the presence of its approval payload. A tool that carries one always blocks for human consent, so you can tell from configuration alone whether a granted tool can act without a human. Its retryability states whether a timed-out call may be reported as a plain failure: reads yes, mutations never. Retrying a mutation that may have landed risks doing it twice. Reads such as search, fetch, list, and read mail are generally ungated. Anything externally visible or irreversible gates. Two tools are core and always available, `skills::load` and `triggers::resolve`. They are framework machinery, not capability anyone grants.

One rule sits above all of it: the model never supplies authority parameters. Any argument that determines whose authority an action carries is fixed in the toolset's settings. That includes the from address on outbound mail and credentials for an external service. An agent may ask that mail be sent. It can't choose who the mail is from.

## Browsing, treated honestly

The web toolset drives a real rendered browser in a session scoped to the turn. `web::navigate`, `web::click`, and `web::fill` each return the page as readable text. It can search, submit forms, and sign in where a task calls for it. A browser that can't do those things is a tool for reading front pages.

Browsing is ungated, which makes it the widest ungated surface in the system. This page names that plainly rather than hiding it. An agent that browses can transmit information on its own authority. A per-action approval would stall every autonomous step while approving only an entry URL, never the later action that mattered. The compensating controls are structural. The status post traces every action live. Credentials are never disclosed. Text typed into a login field is masked in the status post and the trace. A page snapshot reports that a field holds text, but never which text. Scope is enforced rather than requested. Only public web addresses are reachable, never local files or the deployment's own network. Sessions are disposable: cookies and logins die with the turn.

Which agents browse at all is a per-agent grant. An agent whose role doesn't need the web doesn't have the tool.

## Skills

A skill is a procedure document: Markdown, authored by you, stored with the deployment. A toolset may ship skills of its own, granted under its namespace, such as `bookmark::saving-bookmarks`. Framework skills that belong to no capability keep bare names, and the core ones are in every agent's manifest without being granted. Each agent's context carries a skill manifest: the names of its assigned skills with one line of description each. The full body loads on demand. The manifest is what makes on-demand loading safe. An agent may misjudge when a procedure applies, which is an ordinary error. It can never be unaware that the procedure exists, which would be a structural blind spot.

Agents can't write skills. Skill authorship is an administrative act, like everything else that shapes an agent's instructions. Where a procedure's step ordering is load-bearing, it doesn't belong in a skill at all. Checking the ledger before drafting, or logging after sending, is that kind of step. A procedure in prose is a suggestion, and the model will eventually skip the step that mattered. Encode it as a tool, or as a plugin, where the order is code.

## Memory

Each agent has a private memory: entries with a description and a body. Descriptions load into the agent's context every turn. Bodies are fetched on demand. The memory toolset's settings bound memory on every axis: entry count, description length, body length. An over-length write is refused rather than truncated, and a write at the entry cap evicts the oldest entry. Memory is never shared between agents.

Memory writes are the one ungated write in the system. Gating them would park an entire turn on human latency for a triviality: an agent stalled for hours because it wanted to record a phone preference. Memory formation either happens at the moment or doesn't happen.

The compensating control is disclosure. Every memory write emits a line in the status post showing the description and body it stored. An eviction emits a line naming what it displaced. This is detection rather than prevention. The write has already happened when the line appears. Anyone in the channel can review an agent's memory and prune it.

One property is worth knowing: memory is the single path by which information crosses channels. Context is otherwise strictly channel-scoped, but something learned in one channel appears in the agent's memory descriptions everywhere. That is intentional. A colleague who forgot everything between rooms would be useless. It is also the reason memory gets a disclosure line while ordinary reads don't.
