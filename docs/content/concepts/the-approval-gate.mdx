## What an Approval Is

An approval is a blocking request for human consent. When an agent reaches a consequential action, the turn stops. A prompt appears in the channel under the agent's own account, showing the proposed action with its complete payload and buttons. The turn holds until a human answers.

There are three answers.

- **Approve.** The tool executes and the turn continues.
- **Deny.** The turn ends, and the agent posts asking how to proceed. The model does not receive the denial as a tool result. Feeding a bare denial back would send it to the nearest alternative path, producing a series of near-identical proposals.
- **Deny with reason.** The agent receives your reason as the tool's result, and the turn continues under the same budget. Use this to redirect the agent, for example "not that recipient, use the shared address".

Once resolved, the framework rewrites the prompt into its terminal state and removes the buttons. Nobody can click a decided prompt again.

## The Full Payload

The prompt shows the payload itself, not a summary of it: every recipient of an email and its entire body, or the whole file about to be written. Where a payload exceeds what one post can carry, the prompt shows a bounded prefix inline and attaches the complete payload. Shell commands are never attached and never truncated. They appear inline and in full, and the framework refuses a command too long to present.

The approver can only check what they can read, so the prompt shows everything.

## No Timeout

An approval has no timeout. The agent waits for hours or days if it must, and work addressed to it queues visibly behind the pending decision. A gate that expires pressures people to answer fast.

## Who May Answer

Any human present in the channel may decide. There is no separate approver list. A configured roster would be a second access-control system that drifts out of sync with channel membership. You manage membership in one place, the chat client, and the framework verifies each decision against membership before honoring it.

## The Action Budget

Each turn carries an action budget: ten attempts. An attempt is one model-emitted tool invocation, including invocations a human denies before execution. Loading a skill, reading a memory body, and posting don't count.

On exhaustion, the agent posts what it has and asks for an extension. Approving grants ten more attempts with all accumulated context preserved. Each extension prompt carries the running count. Denying an extension ends the turn's actions but not its voice. A denial with reason lets the agent conclude in words with zero attempts remaining, so "stop and report what you have" gets exactly that. A reason never adds attempts.

The ceiling exists because reads don't gate. An agent can run forty searches without touching the gate, and the first visible sign would be whatever it concluded. Frequent budget hits are themselves information: the task is too large or the tools are too fine-grained.

## Approval Frequency

Approval quality falls as approval frequency rises. A gate that fires on every step gets answered without reading within a day. Three things keep prompts infrequent: reads don't gate, the status post carries everything ungated, and the budget prompt arrives only at real boundaries. When a prompt does appear, it is infrequent enough to read.
