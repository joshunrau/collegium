## The status post

Each turn produces one status post, edited in place as the turn progresses. Tool calls append as they happen. Each line names the tool and what the call is doing: the URL being visited, the path being written, the search being run. By the end of a turn, the post reads as a compact trace of what the agent did. While the turn runs, connected clients watch it update live.

One post rather than a stream is deliberate. A ten-call turn streamed as ten posts would bury one post of substance under ten of machinery, in the same channel where approval prompts live. Noise in the supervision channel degrades the gate.

Two quieter signals round it out. A typing indicator shows while the model is generating, and only then. During tool execution and pending approvals, the status post and the prompt already account for the time. A 👀 reaction acknowledges a message that queued behind a busy agent.

Every memory write emits a disclosure line in the status post showing what it stored. An eviction emits a line naming what it displaced.

## The trace

The status post is the summary; `/trace` is the whole record. Invoked on a turn, it returns every tool call with complete arguments and results. The response is ephemeral, visible only to the person who asked. Traces carry file contents and email bodies verbatim, and a channel where everyone can approve is not a channel where everyone needs every payload. Where a trace exceeds what one post can carry, it arrives as an attachment, still ephemeral.

Traces are also the tuning instrument. Reading what agents do with their tools shows you the grant that is never used, the tool that is too coarse, and the task that consistently burns budget.

## One store, authoritative

Conversation content lives authoritatively in SQLite, not in Mattermost. Context assembly reads only the store. The chat API is never on that path.

The reason is what context is: posts interleaved with the agent's own tool calls, tool results, approval decisions, and per-turn metadata, in one order. None of that exists in Mattermost except as rendered text. Kept in two systems, every turn would begin with a merge across different clocks and identifier spaces. Kept in one ordered store, assembly is a read.

The store also imposes honesty about gaps. On boot, the framework backfills posts made while the process was down, per channel and using each agent's own credentials. No agent's store ever contains a channel it couldn't see. Three losses are accepted and documented rather than papered over. Editing a post doesn't correct what an agent already read during uptime. Deleting a post doesn't redact it from context. An agent added to a channel has no history from before it joined.

## Thinking is not stored

A model's private reasoning is never posted, never included in an approval prompt, never written to the store, and never returned by `/trace`. At most, the framework records how many reasoning tokens a provider billed. The system supervises what agents do and say, and the record contains exactly that.

## The command surface

You operate supervision through slash commands in the channel. `/trace` returns the full record. `/queue` and `/triggers` show what is pending. `/forget` and `/reset` repair context. `/stop`, `/kill`, and `/resume` intervene. Memory review prunes what an agent has retained. Repair happens in the channel rather than in a database console so that it stays visible and attributable.
