Collegium runs as one container beside a Mattermost server you already administer. This page takes a
workspace from nothing to a single agent that answers in a channel and stops for approval before it
acts. The [specification](/docs/specification) is the authoritative description of everything below.

You need Docker on the same host as the Mattermost server, an administrator account on that server,
and an API key for [OpenRouter](https://openrouter.ai/keys) or
[DeepSeek](https://platform.deepseek.com/api_keys).

## Provision in Mattermost

The framework creates no accounts and no channels. Provisioning is an administrative act, and
everything below is done before the app first starts.

Under **Integrations → Bot Accounts**, create two bot accounts and mint a token for each — the token
is shown once:

- **The system bot.** It posts status notices and owns the slash-command surface, which it
  reconciles against Mattermost at every boot. It must hold authority to manage the team's slash
  commands (`manage_slash_commands` — team admin is enough); boot refuses without it.
- **One bot per agent.** Its username is the agent's identity, a lowercase slug, and must equal the
  `username` the agent is configured under.

Then create the main channel — where the system bot posts status, and the one channel in which
agents answer only when explicitly `@`-mentioned — and add every bot to the team and to that
channel. The channel id is in **View Info**.

## Configure

```sh
git clone https://github.com/joshunrau/collegium.git
cd collegium
cp .env.template .env
```

`.env` states where the app binds and where its configuration lives; the rest of the template serves
development alone.

```sh
APP_HOST=127.0.0.1
APP_PORT=3000
CONFIG_PATH=./config.json
```

The decision, command, and trigger endpoints trust the network, so bind the loopback or an interface
only the Mattermost server can reach.

`config.json` is the whole deployment: every agent, every grant, every credential.

```json
{
  "$schema": "./app/config.schema.json",
  "mattermost": {
    "mainChannelId": "8f4k2m9x7c3r5t1w6y0qz2n5v8",
    "systemBotToken": "…",
    "url": "https://mattermost.example.com"
  },
  "models": {
    "openrouter": { "apiKey": "…" }
  },
  "agents": [
    {
      "botToken": "…",
      "expertise": "Billing questions and customer mail",
      "model": { "name": "anthropic/claude-sonnet-5", "provider": "openrouter" },
      "systemPrompt": "You are Jane, a support colleague at Northgate.",
      "tools": ["read_memory", "write_file", "write_memory"],
      "username": "jane"
    }
  ]
}
```

Every field is described in `app/config.schema.json`, which the `$schema` line points your editor
at. Four things decide how a first deployment behaves:

- **`tools`** is the agent's entire reach — `browser`, `load_skill`, `mail`, `read_memory`,
  `resolve_trigger`, `shell`, `write_file`, `write_memory`. A tool not listed cannot be called. The
  memory pair is what makes an agent persistent rather than amnesiac; `shell` and `mail` are grants
  you make deliberately, and `mail` additionally requires a configured `mailbox`. Which of them stop
  for a human is the tool's own decision, not a setting: `shell` and `write_file` always do, `mail`
  does on send and reply, and reading — the browser, memory, a mailbox — never interrupts you.
- **`expertise`** is shown to every other agent, so they know when to hand work over.
- **`channels`** sets per-channel triggering mode. Any channel absent from it is mention-required,
  which is why a first config can omit it entirely.
- **`app`** holds the framework-wide bounds — context budget, debounce window, memory caps, the
  hourly turn ceiling — each with a default, so it can be omitted until one of them is wrong for
  you.

## Run

```sh
docker compose up -d
```

That pulls `ghcr.io/joshunrau/collegium:latest`; pass `--build` to build the working tree instead.

The container starts as root and does everything a host would otherwise be responsible for: it
stages the configuration, claims the state directories under `./state`, creates one confined OS user
per shell-granted agent, applies migrations, and drops privileges — irreversibly, once — before the
app itself starts.

Boot then refuses, loudly, on anything it cannot honour: configuration that does not validate, a
granted tool or skill that does not exist, a channel whose membership contradicts what is
configured, or a slash-command surface it cannot reconcile. A framework that starts without its stop
switch is worse than one that does not start.

The first failure most deployments hit is a `CONFIG_PATH` that points nowhere. Docker materialises a
missing bind mount as an empty directory, so it arrives as `"…" is not a file`. Logs are JSON on
stdout:

```sh
docker compose logs -f
```

## The first turn

Mention the agent in the main channel. A typing indicator shows while the model is generating, and
the turn accumulates one status post, edited in place, naming each tool call and what it did.

The moment worth watching for is the first consequential action — ask this agent to write a file.
Instead of writing it, it posts the full payload with **Approve** and **Deny** buttons and waits,
for days if that is how long you take. Any human in the channel may answer; a denial can carry a
reason, which comes back as the tool result and lets the turn continue under the same budget. What
it will never do is work around you: a mutation whose outcome is unknown is reported as unknown, and
a turn that cannot continue ends and says why.

From here, `/trace {post-id}` shows the untruncated tool trace for any turn, and `/stop`, `/kill`,
and `/resume` are the intervention surface. The [specification](/docs/specification) covers the
execution model in full.
