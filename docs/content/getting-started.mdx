title: Getting Started

Collegium runs as a Docker Compose stack: the framework, a Mattermost server, and the Postgres that
serves it. This page takes a workspace from nothing to a single agent that answers in a channel and
stops for approval before it acts. The [specification](/docs/specification) is the authoritative
description of everything below.

You need Docker and an API key for [OpenRouter](https://openrouter.ai/keys) or
[DeepSeek](https://platform.deepseek.com/api_keys). You do not need a Mattermost server; the stack
brings one up and provisions it.

## Configure

```sh
git clone https://github.com/joshunrau/collegium.git
cd collegium
cp .env.template .env
```

`.env` holds everything the deployment needs from you, and nothing that is a fact of the stack.

```sh
MATTERMOST_ADMIN_EMAIL=you@example.com
MATTERMOST_ADMIN_PASSWORD=a-password-you-choose
MATTERMOST_ADMIN_USERNAME=you
MATTERMOST_TEAM=collegium
POSTGRES_PASSWORD=another-password
```

That administrator is created on the first start — Mattermost grants system admin to the first user
of a fresh install — and it is how you log in. Provisioning uses those credentials to create the
team, the bot accounts, and their access tokens; the app itself never holds them, because the
entrypoint drops them from the environment before starting it.

`config.json` declares the deployment: every agent, every grant, every model key. It names no
tokens and no channel ids — provisioning mints the one and resolves the other.

```json
{
  "$schema": "./app/config.schema.json",
  "models": {
    "openrouter": { "apiKey": "…" }
  },
  "agents": [
    {
      "expertise": "Billing questions and customer mail",
      "model": { "name": "anthropic/claude-sonnet-5", "provider": "openrouter" },
      "systemPrompt": "You are Jane, a support colleague at Northgate.",
      "tools": ["read_memory", "write_file", "write_memory"],
      "username": "jane"
    }
  ]
}
```

The `mattermost` block is absent because both of its fields default: the main channel to
`town-square`, and the orchestrator's bot account to `orchestrator`. Every field is described in
`app/config.schema.json`, which the `$schema` line points your editor at. Four things decide how a
first deployment behaves:

- **`tools`** is the agent's entire reach — `browser`, `load_skill`, `mail`, `read_memory`,
  `resolve_trigger`, `shell`, `write_file`, `write_memory`. A tool not listed cannot be called. The
  memory pair is what makes an agent persistent rather than amnesiac; `shell` and `mail` are grants
  you make deliberately, and `mail` additionally requires a configured `mailbox`. Which of them stop
  for a human is the tool's own decision, not a setting: `shell` and `write_file` always do, `mail`
  does on send and reply, and reading — the browser, memory, a mailbox — never interrupts you.
- **`expertise`** is shown to every other agent, so they know when to hand work over.
- **`channels`** sets per-channel triggering mode, naming each channel by handle. Any channel absent
  from it is mention-required, which is why a first config can omit it entirely.
- **`mattermost.mainChannel`** is a handle too, defaulting to `town-square`. A handle naming no
  channel in the team is a boot refusal, not a channel that silently never triggers.
- **`app`** holds the framework-wide bounds — context budget, debounce window, memory caps, the
  hourly turn ceiling — each with a default, so it can be omitted until one of them is wrong for
  you.

## Run

```sh
docker compose up -d
```

Postgres starts, then Mattermost, then the framework — each waiting for the one before it to report
healthy. The first start takes a minute or two while Mattermost builds its schema.

The app's container starts as root and does everything a host would otherwise be responsible for: it
stages the configuration, claims the state directories under `./state`, creates one confined OS user
per shell-granted agent, applies migrations, and drops privileges — irreversibly, once. It then runs
provisioning as its own process, which signs in as your administrator and brings Mattermost into
line with what `config.json` declares: the team, the channels, the orchestrator's bot account and
one per agent, each with an access token kept in the framework's own store. Mattermost reveals a
token once, so those rows in `./state/data` are the only copies; a backup that omits them costs you
a round of re-provisioning, nothing more.

Provisioning is safe to repeat and runs on every start, creating only what is missing. It is a
separate process from the app on purpose: it converges Mattermost onto the declaration, and boot
then refuses anything that does not already match. A boot that verified its own writes would verify
nothing.

Mattermost is at `http://localhost:8065`. Log in with the administrator from `.env`.

Boot then refuses, loudly, on anything it cannot honour: configuration that does not validate, a
granted tool or skill that does not exist, a channel whose membership contradicts what is
configured, or a slash-command surface it cannot reconcile. A framework that starts without its stop
switch is worse than one that does not start.

The first failure most deployments hit is a `CONFIG_PATH` that points nowhere. Docker materialises a
missing bind mount as an empty directory, so it arrives as `"…" is not a file`. Logs are JSON on
stdout:

```sh
docker compose logs -f
```

## The first turn

Mention the agent in the main channel. A typing indicator shows while the model is generating, and
the turn accumulates one status post, edited in place, naming each tool call and what it did.

The moment worth watching for is the first consequential action — ask this agent to write a file.
Instead of writing it, it posts the full payload with **Approve** and **Deny** buttons and waits,
for days if that is how long you take. Any human in the channel may answer; a denial can carry a
reason, which comes back as the tool result and lets the turn continue under the same budget. What
it will never do is work around you: a mutation whose outcome is unknown is reported as unknown, and
a turn that cannot continue ends and says why.

From here, `/trace {post-id}` shows the untruncated tool trace for any turn, and `/stop`, `/kill`,
and `/resume` are the intervention surface. The [specification](/docs/specification) covers the
execution model in full.
