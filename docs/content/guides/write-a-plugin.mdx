Key business logic should be deterministic code, not prompt text. A procedure in a prompt is a suggestion the model will eventually skip; a plugin is TypeScript the framework runs exactly as written, and it will not change under the operator. This guide builds `contacts`: a small address book agents can read freely and update only with approval.

Prerequisites: a running deployment and a working Node.js checkout of the repository.

## What a plugin is

An operator-supplied workspace package, named in `config.json` and loaded once at boot. A plugin is a toolset: a namespace owning tools, skills, settings, and durable records. It cannot change how agents activate, how turns are ordered, or how approvals resolve. Its contributions appear under its namespace (`contacts::save`), and installing a plugin grants it to no one: agents opt in per grant, exactly as with framework capability.

Plugins are trusted code. A plugin runs with framework privilege, so installing one is the same kind of act as editing the framework itself: review it the way deployed code is reviewed. A coding agent can write the first draft of a plugin; the operator's review and install are what make it live, and nothing lets a Collegium agent install, configure, or enable one.

## 1. Scaffold the package

```
plugins/contacts/
  package.json
  src/
    index.ts
```

`package.json`:

```json
{
  "name": "@collegium/plugin-contacts",
  "type": "module",
  "version": "0.0.0",
  "exports": { ".": "./src/index.ts" },
  "dependencies": { "@collegium/sdk": "workspace:*" }
}
```

The SDK is the plugin's only dependency and its only import. What the SDK does not export, a plugin cannot touch.

## 2. Declare the toolset

`src/index.ts` default-exports one toolset — the same declaration a framework capability uses, narrowed to the plugin surface:

```ts
import { defineToolset, fail, ok, z } from '@collegium/sdk';

export type $Contact = z.infer<typeof $Contact>;
export const $Contact = z.object({
  email: z.email(),
  name: z.string().min(1)
});

export type $ContactsSettings = z.infer<typeof $ContactsSettings>;
export const $ContactsSettings = z.strictObject({
  maxContacts: z.number().int().positive().default(200)
});

export default defineToolset({
  name: 'contacts',
  settings: $ContactsSettings,
  storage: { contacts: $Contact },
  tools: {
    find: {
      description: 'Find saved contacts by name.',
      execute: async (args, { storage }) => {
        const contacts = await storage.contacts.list();
        const matches = contacts.filter(({ value }) => value.name.toLowerCase().includes(args.query.toLowerCase()));
        if (matches.length === 0) return ok('no contacts matched');
        return ok(matches.map(({ key, value }) => `- ${key}: ${value.name} <${value.email}>`).join('\n'));
      },
      parameters: z.object({
        query: z.string().min(1).describe('Name or fragment to search for')
      }),
      retryable: true
    },
    save: {
      approval: (args) => ({
        body: `save contact "${args.id}": ${args.name} <${args.email}>`,
        presentation: 'verbatim'
      }),
      description: 'Save or update a contact.',
      execute: async (args, { settings, storage }) => {
        const existing = await storage.contacts.list();
        if (existing.length >= settings.maxContacts) {
          return fail.invalidArguments(`contact limit of ${settings.maxContacts} reached; delete one first`);
        }
        await storage.contacts.put(args.id, { email: args.email, name: args.name });
        return ok(`contact ${args.id} saved`);
      },
      parameters: z.object({
        email: z.email().describe('Email address'),
        id: z.string().min(1).describe('Short identifier to save under'),
        name: z.string().min(1).describe('Full name')
      }),
      traceDetail: (args) => `${args.id}: ${args.name}`
    }
  }
});
```

The declaration is stated once and everything derives from it. Each tool's `args` and context are typed from the declaration itself — `settings` from the settings schema, `storage.contacts` from the collection schema — so a tool cannot disagree with what its toolset declares. Records are validated against the collection schema on write and parsed against it on read, because rows may outlive the schema that wrote them.

Two shapes carry the model's whole gate. `find` has no `approval`, so it never gates — ungated is not unsupervised: every call still appears line by line in the status post and the trace, and the read is marked `retryable` where a mutation never is. `save` has an `approval`, so it always gates, and the function renders the payload a human decides on: show everything the action will do, because a payload nobody can read is a payload nobody is checking.

A plugin may also ship skills — `skills: ['saving-contacts']`, each backed by `skills/<name>.md` beside the entry module and granted as `contacts::saving-contacts`; the in-repo `bookmark` plugin exercises that part of the contract.

## 3. Load, grant, configure

In `config.json`, declare the plugin, grant it to Clara, and set her settings for it — the same `toolSettings` mechanism every toolset uses:

```json
"plugins": [{ "name": "contacts", "path": "./plugins/contacts" }]
```

```json
"tools": ["web", "workspace", "memory", "contacts"],
"toolSettings": {
  "contacts": { "maxContacts": 500 }
}
```

A namespace grant covers every tool the plugin holds, including ones a later version adds; grant `"contacts::find"` instead to hand out one tool. Settings merge shallowly over `app.defaultToolSettings.contacts` and are parsed against the schema the plugin declares — settings for an ungranted toolset are refused, as are settings its schema rejects.

Failures are startup failures. An entry that will not import, a toolset the schema rejects, settings the declared schema refuses, a grant nothing provides: each stops the process from starting and names the plugin. Nothing about a plugin is discovered mid-turn.

## 4. Try it

Restart the deployment, then:

> @clara Save Elena Baptiste, elena@northshoresummit.co, as our Northshore Summit contact.

The approval prompt shows exactly what will be written. Approve it, then:

> @clara Who do we know at Northshore Summit?

The find runs without a gate, and the answer comes back from the plugin's own records.
