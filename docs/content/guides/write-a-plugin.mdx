---
title: Write a Plugin
description: 'Ship business logic as deterministic code: storage, an ungated read, a gated write, and settings.'
---

A plugin is a directory of TypeScript that the deployment compiles at boot. It contributes a toolset: a namespace of tools, skills, settings, and durable records, granted to agents like any built-in toolset. This guide builds `contacts`: an address book agents can read freely and update only with approval.

Prerequisites: a running deployment, and Node.js wherever you write the plugin. You don't need a checkout of Collegium.

Plugins run with framework privilege. Review a plugin before you install it, the same way you review any deployed code.

## 1. Scaffold the package

```sh
mkdir contacts && cd contacts
npm init --yes
npm install @collegium/sdk
```

Set `type`, `exports`, and `dependencies`:

```json
{
  "name": "contacts",
  "type": "module",
  "version": "0.0.0",
  "exports": "./src/index.ts",
  "dependencies": { "@collegium/sdk": "^0.0.1-beta.4" }
}
```

The framework checks three things at boot and refuses to start if any fails:

- `exports` is a plain string naming a TypeScript entry file, or an object whose `"."` is one. Don't build it; the framework compiles it.
- `@collegium/sdk` is the only entry in `dependencies`. Put `typescript`, `vitest`, and other tooling in `devDependencies`.
- The `@collegium/sdk` range matches the deployment's version.

## 2. Declare the toolset

`src/index.ts` default-exports one toolset:

```ts
import { defineToolset, fail, ok, z } from '@collegium/sdk';

export type $Contact = z.infer<typeof $Contact>;
export const $Contact = z.object({
  email: z.email(),
  name: z.string().min(1)
});

export type $ContactsSettings = z.infer<typeof $ContactsSettings>;
export const $ContactsSettings = z.strictObject({
  maxContacts: z.number().int().positive().default(200)
});

export default defineToolset({
  name: 'contacts',
  settings: $ContactsSettings,
  storage: { contacts: $Contact },
  tools: {
    find: {
      description: 'Find saved contacts by name.',
      execute: async (args, { storage }) => {
        const contacts = await storage.contacts.list();
        const matches = contacts.filter(({ value }) => value.name.toLowerCase().includes(args.query.toLowerCase()));
        if (matches.length === 0) return ok('no contacts matched');
        return ok(matches.map(({ key, value }) => `- ${key}: ${value.name} <${value.email}>`).join('\n'));
      },
      parameters: z.object({
        query: z.string().min(1).describe('Name or fragment to search for')
      }),
      retryable: true
    },
    save: {
      approval: (args) => ({
        body: `save contact "${args.id}": ${args.name} <${args.email}>`,
        presentation: 'verbatim'
      }),
      description: 'Save or update a contact.',
      execute: async (args, { settings, storage }) => {
        const existing = await storage.contacts.list();
        if (existing.length >= settings.maxContacts) {
          return fail.invalidArguments(`contact limit of ${settings.maxContacts} reached; delete one first`);
        }
        await storage.contacts.put(args.id, { email: args.email, name: args.name });
        return ok(`contact ${args.id} saved`);
      },
      parameters: z.object({
        email: z.email().describe('Email address'),
        id: z.string().min(1).describe('Short identifier to save under'),
        name: z.string().min(1).describe('Full name')
      }),
      traceDetail: (args) => `${args.id}: ${args.name}`
    }
  }
});
```

- `settings` types the `settings` argument each tool receives. Agents set values under `toolSettings.contacts`.
- `storage` declares one collection per key. Each tool receives it typed, and reads and writes are validated against the schema.
- A tool with `approval` blocks for a human decision on every call. The function returns the payload the human sees; include everything the action will do.
- A tool without `approval` runs without a gate. Mark it `retryable` only if a timed-out call is safe to report as a failure. Never mark a mutation retryable.
- `traceDetail` is the one-line summary shown in the status post.

### What you may import

Import `@collegium/sdk`, `node:` builtins, and your own files by relative path. The compiler refuses any other bare specifier at boot.

Import `z` from `@collegium/sdk`, not from `zod`.

`fetch`, `crypto`, `Intl`, and `structuredClone` are available as globals.

To ship skills, declare `skills: ['saving-contacts']` and add `src/skills/saving-contacts.md` beside the entry module. Agents get the skill via the grant `contacts::saving-contacts`. See the in-repo `bookmark` plugin for an example.

## 3. Install it

Clone the plugin into the directory `PLUGINS_ROOT` in `.env` points at. In a clone of Collegium, that is `plugins/`:

```sh
git clone https://github.com/you/contacts plugins/contacts
```

The subdirectory name must equal the toolset's `name`. The framework refuses to boot if they differ.

## 4. Grant and configure

In `config.json`, declare the plugin:

```json
"plugins": ["contacts"]
```

Then grant it to Clara and set her settings for it:

```json
"tools": ["web", "workspace", "memory", "contacts"],
"toolSettings": {
  "contacts": { "maxContacts": 500 }
}
```

`"contacts"` grants every tool in the plugin, including ones a later version adds. Grant `"contacts::find"` instead to hand out one tool. Settings merge over `app.defaultToolSettings.contacts`. The framework refuses settings for an ungranted toolset and settings the schema rejects.

## 5. Try it

Restart the deployment, then:

> @clara Save Elena Baptiste, elena@northshoresummit.co, as our Northshore Summit contact.

The approval prompt shows exactly what will be written. Approve it, then:

> @clara Who do we know at Northshore Summit?

The find runs without a gate, and the answer comes back from the plugin's records.
